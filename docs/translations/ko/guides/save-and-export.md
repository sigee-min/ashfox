`.ashfox` 파일, 가져오는 모든 모듈, 선택적인 `.ashfoxworkspace`를 함께 버전 관리하세요. 이 파일들이 편집 원본입니다. 생성된 GLB·PNG·WAV·OGG·ZIP은 재빌드할 수 있으며 원본 백업을 대신하지 않습니다.

## 프로젝트 출력 파일 선택하기

개별 파일에는 `exports`, 게임용 파일 배치에는 `packs`를 사용합니다. [프로젝트 설정](workspace.md)에서 경로와 ID를 정한 뒤 `build`를 실행하세요. 소스 변경이 기존 출력을 자동으로 재빌드하지는 않습니다.

엔진 전달은 `result.exports`에서 팩 ID를 찾아 `game-assets` 폴더나 ZIP을 복사합니다. Minecraft는 `resource-pack` 폴더나 ZIP을 복사합니다. 설정한 대상 디렉터리 전체를 복사하지 마세요. 버전별 빌드와 소유권 메타데이터도 포함되어 있습니다. [출력 포맷](choose-a-format.md)을 참고하세요.

## 정확히 하나의 빌드 선택하기

빌드 디렉터리의 `current.json`은 완전한 `bundles/<hash>` 하나를 가리킵니다. 게임 빌드마다 포인터를 한 번 읽거나 성공한 `build`가 반환한 `bundleHash`와 경로를 사용하세요. 수정 시각으로 선택하거나 두 해시의 파일을 섞지 마세요.

검증은 정식 파일 해시, 메타데이터, 정확한 파일 구성을 검사합니다. 일반 게임 팩의 런타임 매니페스트는 참조 파일과 일치해야 합니다. 소스를 재컴파일하거나 시청각 품질을 인증하는 작업은 아닙니다.

## 실패한 빌드와 정리

팩 실패, 오래된 소스, 취소, 인코딩 실패는 이전 포인터를 바꾸지 않습니다. 실패 후 선택되지 않은 완성 번들이 남을 수 있지만 파일이 존재한다고 발행에 성공한 것은 아닙니다.

자동 정리는 없습니다. 소비 중인 빌드가 없을 때만 오래된 생성 번들을 제거하세요. 선택된 번들과 대응 export 복사본은 유지합니다. 새 빌드는 새 빈 출력 디렉터리를 쓰거나 지워도 되는 생성 트리만 제거하세요. 소스를 삭제하거나 영수증을 직접 편집하지 마세요.

CLI는 알 수 없는 비어 있지 않은 디렉터리의 소유권을 가져오지 않습니다. export 복사본은 발행 중 검증하고 `verify`는 정식 빌드를 검사합니다. 전달 복사본을 이후 수정했다면 검증된 정식 출력에서 다시 복사하거나 카탈로그 해시와 비교하세요.
